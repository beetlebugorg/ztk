Stage 1 Experimental · BSD-2-Clause

Tk, rebuilt in Zig.

ztk runs Tk scripts on the ztcl interpreter, with a GPU renderer and stylesheets in a subset of CSS. Stage 1 is a working demo on Linux.

Get started GitHub

The goal: a script that runs in wish 8.6 runs in ztk with no change. The test files of Tk 8.6.16 measure it.

demo.tcl
label .title -text "Hello from ztk"
entry .name -textvariable name -width 24
button .greet -text "Greet" \
    -command {set msg "Hello, $name!"}
label .msg -textvariable msg
grid .title -sticky w -padx 12 -pady 6
grid .name .greet -sticky ew -padx 12 -pady 4
grid .msg - -sticky w -padx 12 -pady 6
bind .name <Return> {.greet invoke}
/* demo.css */
#greet {
  color: var(--accent-fg);
  background-color: var(--accent);
}
#greet:hover { background-color: var(--accent-hover); }

What it draws

Tk scripts, drawn by ztk.

Each image is one frame of an example script, drawn by the CPU renderer on the headless backend at scale 2. The images follow the color scheme of your system. Each script also runs in wish 8.6.

Make the images again with zig build and tools/shots.sh. One image: ztk --headless --scale 2 --exit-after-frames 1 --screenshot out.png script.tcl, with --dark for the dark scheme.

Performance

Each target of the plan has a number.

The plan sets a budget for frame time, start time, memory, and size. The Stage 1 report measures each one, and it also lists the targets that Stage 1 missed.

No frames when idle

A window with no change draws no frame and wakes no thread. The tests counted 0 frames in 5 000 ms of the manual clock.

A render thread

The UI thread runs the script and makes a scene: a plain list of quads. The render thread draws the scene. The UI thread does not wait for it, except in update.

Small changes write few rows

On the framebuffer, the CPU renderer writes only the rows that changed. A test checks that a small change writes less than 10 % of the rows.

The frame rate on a real display is not measured yet. The Stage 1 report has each command and each result.

Native GPU rendering

One renderer for each platform API.

Each platform draws with its own GPU API, with no translation layer between ztk and the driver. ztk does not use MoltenVK, ANGLE, or DXVK. A CPU renderer gives the same image on each machine, and the tests compare the GPU output with it.

Works

CPU renderer

The reference renderer. It draws the demo into a Wayland shared memory buffer and into a framebuffer.

Works offscreen

Vulkan on Linux

The Vulkan renderer matches the CPU renderer on two GPUs, within 2 levels. The swapchain on a window is not written yet.

Modern features

Style Tk widgets with CSS.

A stylesheet in a subset of CSS gives the default look. Your stylesheet changes it, with selectors, states, variables, and transitions.

  • A modern theme from a stylesheet, with a dark scheme.
  • A font engine with no library. It reads TrueType outlines and the kerning of the GPOS table.
  • A classic theme with the sizes and colors of Tk is planned.
style.css
Button {
  border-radius: 6px;
  padding: 6px 12px;
  transition: all 120ms;
}
Button:hover {
  background: var(--accent);
  color: var(--accent-fg);
}

Built on ztcl

The sandbox of ztcl, and no third-party library.

ztk adds the Tk commands to ztcl and uses it as a Zig package. It needs only the interfaces of the platform, ztcl, and the Zig standard library.

No capability by default

The ztk library turns on no capability of ztcl. It reaches the host only through its backend. Only the ztk program turns on a capability, from a flag.

One static program

The core, the text code, the headless backend, and the direct backend link no library. The build with the direct and headless backends and no Vulkan is one static program.

Vulkan at run time

No build links the Vulkan loader. The program opens it at run time, so it also starts on a machine with no Vulkan.

Backends

Works

Headless

For tests and for the oracle that compares ztk with wish. The headless program compiles for Linux, macOS, and Windows. Only Linux runs are checked.

Works

Wayland

The CPU renderer into shared memory. Checked on a private headless compositor. A run on a live desktop is not tried yet.

Not tried on a device

Direct

For a Linux device with no display server: the framebuffer and evdev. Tests use fake hosts. --direct needs the flag --direct-unsafe-test-device.

Status

Stage 1 of nine: a demo-sized toolkit.

ztk is not a drop-in Tk yet. The plan, the commands, and the behavior can change at any time. The plan estimates two and a quarter to three and a half years of work for one engineer.

  • Worksframe, label, button, entry, grid, bind, event generate, focus, and wm and winfo for .
  • Worksexamples/demo.tcl runs in ztk and in wish 8.6.16.
  • PartialThe grid solver: 11 of 600 random layouts differ from wish 8.6.16. Two rules of the solver are not found yet.
  • Not yetThe Vulkan swapchain on a window and on a display, and the other widgets and commands of Tk.
  • Not triedA window on a live desktop, and the direct backend on a real device. The tests run on Linux only.
  • ReviewFour independent reviews said "do not merge" or "not yet". The fixes for the fourth review are in the code, and no review has checked them yet.
  • NoteThe code and the docs are written largely with AI coding agents, under human direction. Review the work before you depend on it.
